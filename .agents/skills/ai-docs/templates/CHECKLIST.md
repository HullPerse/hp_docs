# {{PROJECT_NAME}} Implementation Checklist

Используй для каждой нетривиальной задачи. Копируй только релевантные пункты в план задачи.

## Перед кодингом

- [ ] Проверь доступные MCP-серверы и инструменты; для вопросов о библиотеках используй документационный инструмент до ответа из памяти, релевантные задаче инструменты применяй вместо обходных путей.
- [ ] Прочитай `.docs/AGENT_PROMPT.md`.
- [ ] Прочитай `.docs/DEVELOPMENT.md`.
- [ ] Прочитай и проанализируй `.docs/DECISIONS.md` до аудита: проверь принятые решения, ограничения и конфликты.
- [ ] Прочитай `.docs/DESIGN.md`, если затронут UI/UX.
- [ ] Прочитай README и package.json модуля.
- [ ] Поищи существующий код и конвенции проекта.
- [ ] Пройди лестницу ponytail до написания своего решения: переиспользуй соседний код, затем stdlib, затем нативную платформу, затем установленную зависимость; своя реализация - последняя ступень.
- [ ] Проверь `package.json`, lockfile, версии и текущие места использования подходящих пакетов до написания своей реализации.
- [ ] Подтверди, что зависимость уже используется, или зафиксируй, почему нужна новая.
- [ ] Если готового пакета нет, сравни несколько современных вариантов по поддержке, лицензии, размеру и производительности и явно выбери рекомендуемый вариант.
- [ ] Проверь лицензию и поддержку платформы для новых зависимостей.
- [ ] Для каждой новой фичи задай implementation disposition: реализовать сейчас, отложить или отклонить.
- [ ] Для каждой новой фичи отдельно выбери documentation destination: существующий `.docs/features/*.md`, новый `.docs/features/<slug>.md` или только `.docs/DECISIONS.md`.
- [ ] Найди остальные неоднозначные решения и спроси пользователя.
- [ ] Проверь, не является ли предложение ненужным, вредным, преждевременным или чрезмерно сложным; если да, сначала дай прямой verdict, поспорь и предложи лучший путь.
- [ ] Сгруппируй вопросы (без жёсткого лимита, но без мусорных).
- [ ] Проверь labels/descriptions: короткий простой русский, одна мысль, без случайного английского, маркетингового мусора и псевдотехнического жаргона.
- [ ] В multi-select отметь `(recommended)` только реально рекомендуемые отдельные опции и объясни, что marker не означает выбрать все такие опции.
- [ ] Включи последствия, обратимость, безопасность/приватность, производительность, тесты.
- [ ] Определи, блокируют ли неотвеченные выборы реализацию или допустим обратимый safe default.
- [ ] Напиши короткий план реализации.
- [ ] Определи тесты для каждой новой фичи.

## Во время кодинга

- [ ] Один источник истины для стейта.
- [ ] Новые общие типы, helpers, конфиги, хуки и API-клиенты размещены в закреплённых каталогах и названы по принятому суффиксу.
- [ ] Basename файлов компонентов написан в camelCase без дефисов, служебный суффикс сохранён.
- [ ] Минимальное связное изменение, без несвязанных рефакторов.
- [ ] Фикс бага сделан в общем месте корня, а не на одном названном пути; вызывающие проверены grep-ом.
- [ ] Осознанные упрощения с известным потолком помечены комментарием `ponytail:` с путём апгрейда.
- [ ] Не меняй существующее поведение без задачи.
- [ ] Без спекулятивных абстракций и мёртвых точек расширения.
- [ ] Реализуй loading, empty, error, dirty, stale, recovery состояния.
- [ ] Перед новым компонентом поищи аналог в общих каталогах; не создавай дубль без причины.
- [ ] Соответствие `.docs/DESIGN.md` (если применимо).
- [ ] Без секретов в исходниках, логах, файлах рабочей области.
- [ ] Добавляй тесты вместе с фичей, а не после её объявления готовой.

## Проверка

- [ ] Запусти форматтер/стиль: {{LINT_COMMAND}}.
- [ ] Запусти typecheck: {{TYPECHECK_COMMAND}}.
- [ ] Запусти релевантные тесты: {{TEST_COMMAND}}.
- [ ] Зафиксируй одобренное исключение, если слой тестов не может запуститься.
- [ ] Просмотри diff на несвязанные изменения.
- [ ] Массовые правки текстовых файлов выполнены с явной кодировкой UTF-8 ([IO.File]::ReadAllText/WriteAllText), содержимое выборочно перечитано после записи; PS 5.1 Get-Content/Set-Content без указания кодировки портит кириллицу.
- [ ] Проверь на debug-логи, placeholder-данные, мёртвый код, случайные комментарии.
- [ ] Проверь типизацию по правилам языка проекта (раздел "Типизация по языку" в DEVELOPMENT.md): TS - без явного `any`, `unknown` только на boundary со сужением; Rust - Option/Result на границах, unsafe изолирован; Python - без молчаливого Any на публичных границах.
- [ ] Проверь поток данных по зафиксированной модели проекта (query-библиотека или фоновые задачи): состояния берутся из неё, а не дублируются ручным стейтом.
- [ ] Проверь расположение файлов: общие типы в `types/*.d.ts`, helpers в `lib/*.utils.ts`, конфиги в `config/*.config.ts`, хуки в `hooks/**/*.hook.ts`, API-клиенты в `api/**/*.api.ts`.
- [ ] Проверь имена файлов компонентов: camelCase без дефисов до служебного суффикса.
- [ ] Если нужен локальный тип или helper вне этих каталогов, согласуй конкретный путь с пользователем до создания файла.
- [ ] Проверь, что не введены длинные тире (em/en dash).
- [ ] Прогони deslop self-check по текстам (каталог в `.docs/DEVELOPMENT.md`): словарные теги, rule-of-three, хеджирование, throat-clearing, деепричастные хвосты, выдуманная конкретика; голос автора сохранён.
- [ ] Не подменяй критику идеи оскорблением пользователя; у каждого жесткого verdict есть причины, последствия и альтернатива.

## Feature-файлы

- [ ] Если затронут `.docs/features/*.md`, текст написан простыми абзацами и короткими списками.
- [ ] Идея отделена от комментария, плюсов, минусов и альтернатив, если они нужны.
- [ ] Нет таблиц, декоративного форматирования и глубокой вложенности без конкретной пользы.
- [ ] Пример старого и нового кода добавлен только при необходимости и оформлен в fenced code blocks.
- [ ] Для planning-only идеи не добавлен выдуманный код.

## Документация

- [ ] Запиши выбранные implementation disposition и documentation destination в соответствующий feature-файл или `.docs/DECISIONS.md`.
- [ ] Добавь в `.docs/DECISIONS.md` каждое существенное решение, изменение поведения или исправление пользовательского бага до финального отчёта; если таких изменений нет, явно укажи это.
- [ ] Обнови `.docs/DESIGN.md`, если изменились UX/визуальные правила.
- [ ] Обнови README модуля, если изменились команды/структура/конвенции.
- [ ] Для крупных изменений предложи независимое ревью через `.docs/REVIEWER.md`.
- [ ] Сообщи, что проверено и что осталось непроверенным.
