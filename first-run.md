# First-Run: Project Analysis and Template Setup

Этот промпт запускается агентом при ПЕРВОЙ встрече с `AGENTS.md` в проекте, где `.docs/` ещё не заполнен (содержит плейсхолдеры `{{...}}`).

## Цель

Проанализировать проект и заполнить шаблоны `.docs/` конкретными данными о проекте.

## Важно

Все строгие правила из `AGENT_PROMPT.md`, `DEVELOPMENT.md` и `CHECKLIST.md` действуют в полной мере:
- Аудит перед любыми изменениями
- Disposition gate для новых фич
- Anti-slop правила
- Прямой критический режим
- Запись решений в DECISIONS.md

---

## Шаг 0: Определи состояние проекта

Прежде чем заполнять шаблоны, определи: **проект уже существует или создаётся с нуля?**

### Критерии "проект существует":
- Есть `package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod` или аналог
- Есть `src/` или другой каталог с исходниками
- Есть хотя бы несколько файлов кода

### Критерии "проект не существует":
- Нет файлов зависимостей
- Нет исходников
- Только что инициализирован репозиторий (или пустой)

---

## Шаг 1: Сканирование проекта

Прочитай и проанализируй:

1. `package.json` (корневой и в подкаталогах) -- стек, зависимости, скрипты.
2. `Cargo.toml`, `pyproject.toml`, `go.mod` или другой файл зависимостей -- если это не JS/TS проект.
3. `tsconfig.json` / `tsconfig.node.json` -- настройки TypeScript.
4. Структура каталогов: `ls -la`, `find . -maxdepth 3 -type d`.
5. README.md -- описание проекта.
6. `.gitignore` -- что исключено.
7. Основные entry points: `src/main.ts`, `src/index.ts`, `main.go`, `src/main.rs` и т.д.

## Шаг 2: Определение стека

На основе анализа определи:

- **Язык и рамки**: TypeScript/Bun, Python/FastAPI, Rust/Tauri, Go и т.д.
- **Frontend** (если есть): React, Vue, Svelte и т.д.
- **Backend** (если есть): Elysia, Express, Axum и т.д.
- **База данных**: SQLite, PostgreSQL, Redis и т.д.
- **Пакетный менеджер**: npm, pnpm, bun, cargo, pip.
- **Команды dev/test/lint/typecheck/build**: из package.json scripts или эквивалентов.

## Шаг 3: Заполнение плейсхолдеров

Замени все `{{...}}` в файлах `.docs/` на реальные данные проекта:

| Плейсхолдер | Источник данных |
|---|---|
| `{{PROJECT_NAME}}` | Имя из package.json/name или README |
| `{{PROJECT_CONTEXT}}` | Стек + описание из README/package.json |
| `{{PROJECT_OVERVIEW}}` | Краткое описание + структура каталогов |
| `{{FIXED_DECISIONS}}` | Пока пусто или базовые правила из README |
| `{{DIRECTORY_STRUCTURE}}` | Анализ `find . -maxdepth 3 -type d` |
| `{{COMMANDS}}` | Скрипты из package.json |
| `{{DESIGN_PRINCIPLES}}` | Если UI-проект -- базовые принципы, иначе опустить |
| `{{COLOR_TOKENS}}` | Если UI-проект -- из index.css или конфига темы |
| `{{TYPOGRAPHY}}` | Если UI-проект -- шрифт и размеры |
| `{{COMPONENTS}}` | Если UI-проект -- список основных компонентов |
| `{{SPACING}}` | Если UI-проект -- отступы и тени |
| `{{MOTION}}` | Если UI-проект -- анимации |
| `{{A11Y}}` | Если UI-проект -- accessibility правила |
| `{{LINT_COMMAND}}` | `bun run lint` / `cargo clippy` / и т.д. |
| `{{TYPECHECK_COMMAND}}` | `bun run typecheck` / `cargo check` / и т.д. |
| `{{TEST_COMMAND}}` | `bun test` / `cargo test` / и т.д. |

## Шаг 4: Верификация

После заполнения:

1. Запусти `{{LINT_COMMAND}}`, `{{TYPECHECK_COMMAND}}`, `{{TEST_COMMAND}}` чтобы убедиться, что команды работают.
2. Проверь, что описанная структура каталогов соответствует реальности.
3. Проверь, что все зависимости из `{{PROJECT_CONTEXT}}` действительно установлены.

## Шаг 5: Вопрос пользователю -- Глубокий анализ

**Обязательно задай этот вопрос пользователю после заполнения шаблонов:**

---

**Вопрос:**

Проект обнаружен и `.docs/` заполнен. Выбери, что дальше:

1. **Глубокий анализ существующего проекта** -- агент детально проанализирует весь код, зависимости, архитектуру и предложит улучшения (см. Шаг 6).
2. **Пропустить анализ** -- перейти к обычной работе.

---

### Шаг 6: Глубокий анализ (если выбрано)

Если пользователь выбрал глубокий анализ, выполни следующее. **Все строгие правила действуют: аудит, anti-slop, прямой критический режим, запись решений.**

#### 6.1 Анализ кодовой базы

Просмотри основные модули и проверь:

- **Архитектура**: нет ли смешивания ответственности, дублирования логики, спекулятивных абстракций.
- **Типизация**: нет ли `any`, скрытых `unknown`, слабых типов.
- **Обработка ошибок**: есть ли boundary для ошибок, типизированные ошибки, graceful degradation.
- **Состояния**: loading, error, empty, disabled, dirty, stale -- реализованы ли.
- **Тесты**: есть ли покрытие для доменных правил, интеграционные тесты.
- **Безопасность**: секреты в коде, XSS, инъекции, небезопасные зависимости.
- **Производительность**: утечки памяти, неоптимизированные рендеры, отсутствие мемоизации.
- **Anti-slop**: комментарии-пересказы, debug-логи, мёртвый код, placeholder-данные.

#### 6.2 Анализ зависимостей

Проверь `package.json` / `Cargo.toml` / `pyproject.toml`:

- **Устаревшие пакеты**: есть ли замены, которые быстрее/легче/поддерживаются активнее.
- **Дублирование功能**: несколько пакетов для одной задачи (например, два HTTP-клиента).
- **Безопасность**: известные уязвимости в зависимостях.
- **Размер**: тяжёлые пакеты, которые можно заменить на lighter alternatives.
- **Неиспользуемые зависимости**: пакеты в dependencies, которые нигде не импортируются.

Для каждого найденного пакета предложи:
- Текущий пакет и его состояние (активен/устарел/заброшен)
- Альтернативу (если есть) с сравнением: размер, скорость, поддержка, лицензия
- Рекомендацию `(recommended)` только если есть реальное обоснование

#### 6.3 Анализ инструментов и конфигов

Проверь:

- **Линтеры и форматтеры**: актуальны ли конфиги, нет ли конфликтов.
- **TypeScript**: строгость tsconfig, есть ли `strict: true`, unnecessary `@ts-ignore`.
- **Билд-система**: Vite/Webpack/esbuild -- актуальна ли версия, оптимальны ли настройки.
- **Тестовый фреймворк**: Vitest/Jest/pytest -- покрытие, скорость, настройки.

#### 6.4 Формат отчёта

Представь результат в формате:

```
## Глубокий анализ: {{PROJECT_NAME}}

### Структура
Краткое описание архитектуры и организации кода.

### Находки

#### Код
| # | Тип | Файл/Модуль | Проблема | Рекомендация |
|---|-----|-------------|----------|--------------|
| 1 | Архитектура | src/foo.ts | Смешение UI и логики | Вынести логику в hook |
| 2 | Типизация | src/bar.ts | Явный any | Сузить до конкретного типа |

#### Зависимости
| # | Пакет | Текущая версия | Статус | Альтернатива | Рекомендация |
|---|-------|---------------|--------|--------------|--------------|
| 1 | old-http | 1.x | Устарел | modern-http | (recommended) замена |
| 2 | utils | 2.x | Активен | - | оставить |

#### Инструменты
| # | Инструмент | Статус | Проблема | Рекомендация |
|---|------------|--------|----------|--------------|
| 1 | eslint | Устарел конфиг | Миграция на oxlint | (recommended) |

### Итог
- Здоровье проекта: X/10
- Критичные проблемы: N
- Рекомендации по улучшению: N
- Следующий шаг: конкретное действие

### Disposition
- Implementation: [сейчас / отложить / отклонить] для каждого предложения
- Documentation: [существующий feature-файл / новый / DECISIONS.md]
```

#### 6.5 Запись решений

Каждое предложение по улучшению получи `disposition` от пользователя:
- **сейчас** -- реализовать немедленно
- **отложить** -- записать в feature-файл с условиями возврата
- **отклонить** -- записать в DECISIONS.md с причиной

Запиши все решения в `.docs/DECISIONS.md` и соответствующие feature-файлы.

## Шаг 7: Инициализация нового проекта (если проект не существует)

**Если проект не существует (пустой репозиторий или только что создан), задай этот вопрос:**

---

**Вопрос:**

Проект не обнаружен. Выбери:

1. **Предложить стек и инициализировать проект** -- агент предложит оптимальный стек для заявленной задачи и создаст базовую структуру (см. Шаг 8).
2. **Только заполнить .docs/** -- заполнить шаблоны минимальными данными, стек определит пользователь позже.

---

### Шаг 8: Инициализация нового проекта (если выбрано)

Если пользователь выбрал инициализацию, выполни следующее. **Все строгие правила действуют.**

#### 8.1 Определение задачи

Спроси пользователя:
- Какова задача проекта? (веб-приложение, CLI, API, библиотека, бот и т.д.)
- Есть ли предпочтения по стеку? (или доверить выбор агенту)
- Какие платформы обязательны? (desktop, mobile, web, server)
- Есть ли референсы или примеры того, что нужно получить?

#### 8.2 Предложение стека

На основе задачи предложи 2-3 варианта стека с сравнением:

| Критерий | Вариант A | Вариант B | Вариант C |
|----------|-----------|-----------|-----------|
| Язык | TypeScript | Rust | Python |
| Рамки | Bun + Elysia | Axum + SQLx | FastAPI + SQLAlchemy |
| Пакетный менеджер | bun | cargo | pip/uv |
| Скорость | Быстрый | Очень быстрый | Средний |
| Экосистема | Широкая | Растущая | Широкая |
| Learning curve | Низкий | Средний | Низкий |

Пометь `(recommended)` только при реальном обосновании.

#### 8.3 Инициализация

После выбора стека:

1. Создай структуру каталогов
2. Инициализируй зависимости (`bun init`, `cargo init`, `uv init`)
3. Настрой конфиги (tsconfig, Cargo.toml, pyproject.toml)
4. Добавь базовые скрипты (dev, test, lint, build)
5. Создай `.gitignore`
6. Заполни `.docs/` шаблоны с реальными данными нового проекта
7. Запиши все решения в `.docs/DECISIONS.md`

#### 8.4 Верификация

1. Запусти `dev` -- убедись, что проект запускается
2. Запусти `test` -- убедись, что тесты работают (даже если пустые)
3. Запусти `lint` / `typecheck` -- убедись, что конфиги корректны

---

## Шаг 9: Запись в DECISIONS.md

Добавь первую запись (независимо от выбранного пути):

```markdown
### YYYY-MM-DD: Инициализация .docs/ шаблона

- Решение: шаблон `.docs/` заполнен автоматически на основе анализа проекта.
- Контекст: первый запуск агента в проекте {{PROJECT_NAME}}.
- Последствие: агент теперь следует правилам из `.docs/`.
- Источник: first-run анализ.
```

## Шаг 10: Отчёт пользователю

Покажи пользователю:

1. Что было определено (стек, команды, структура).
2. Какие файлы были заполнены.
3. Что осталось пустым (опциональные секции для UI).
4. Предложи проверить и дополнить `.docs/DECISIONS.md` и `.docs/DESIGN.md` при необходимости.

---

## Важно

- Не редактируй `AGENTS.md` при first-run -- он уже универсален.
- Не удаляй `{{...}}` которые не смог заполнить -- пометь их как `<!-- TODO: заполнить вручную -->`.
- Не меняй структуру файлов -- только содержимое плейсхолдеров.
- Все изменения записываются в `.docs/DECISIONS.md`.
- Все строгие правила из `AGENT_PROMPT.md` действуют: аудит, disposition, anti-slop, прямой критический режим.
